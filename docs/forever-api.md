# WoW: Forever client API notes

What we know about the addon API on the WoW: Forever client, where each fact came from, and how sure we are. `AGENTS.md` has the short version; this file has the detail and the sources.

First written 2026-09-25 against build **1.60.1.70009** (the build in the client's `.build.info`, product `wow_classic_beta`). Facts found since name their build and date; the latest Self Test ran on build 70338 (2026-10-14). Forever is a beta: recheck anything marked below before relying on it after a patch.

## How to read the tags

Every fact carries one tag saying how it was established:

| Tag | Meaning |
| --- | --- |
| **[local]** | Read from a Forever client install: its files, installed addons, or saved files. |
| **[in-game]** | Tested in the live client, with `/dump`, `/run`, or a test addon. |
| **[dump]** | Present in a captured API dump of the Forever client (see [Sources](#sources)). Shows the API exists, not that it behaves like Retail. |
| **[addon]** | Inferred from how an installed Forever addon uses it. The addon works for players, but we have not tested that exact call. |
| **[web]** | Reported by someone else online. Not checked by us. |
| **[tables]** | Read from the client's database tables for a named build, as wago.tools publishes them (`tools/datagen/`, write-up in [table-survey.md](table-survey.md)). Shows what the client ships, not what the server does. |
| **Unverified** | Plausible but unconfirmed, or sources disagree. Check before depending on it. |

When you confirm or rule out something here, change its tag, add the date, and say how you checked.

## Client identity

- The live client: build 1.60.1.70755 (2026-11-03; 70707 on 2026-10-30), interface **16001**, product `wowf`, exe `Wow.exe`, folder `_forever_`. **[local]** (`.build.info`, `.flavor.info`, `WTF\Config.wtf` has `engineSurveyPatch "16001"`) Its `WTF` was copied from the beta, so the saved files and realm folders there are the beta's until the live game rewrites them.
  - Every `C_` function, event, and global function the addon names is in build 70755's `Wow.exe` (`strings`) or its Blizzard UI, except `C_Console`, already known to be missing. **[local]** (2026-11-03) Every Blizzard global, hook target, and hooked method it names is in the `forever` branch of wow-ui-source at 70755, except the mail frame's `InboxFrame_Update` and `OpenMail_Update`, which became `InboxFrame:Update()` and `OpenMailFrame:Update()` (`InboxMixin`, `OpenMailMixin`) by 70338. **[web]**
  - 70755 changed bag item buttons' `Initialize(bag, slot)` to `Initialize(containerFrame, bag, slot)`, and gamepad bag slots now show their own free slot count, "(16)". Nothing here hooks either. **[web]** (wow-ui-source 70532...70755)
- The beta client: build 1.60.1.70009, interface **16001**, product `wow_classic_beta`, exe `WowB.exe`, folder `_classic_beta_`. **[local]** (`.build.info`, `WTF\Config.wtf` has `engineSurveyPatch "16001"`)
- Internal codename is **Camelot**. It shows up in TOC suffixes, TOC game types, and addon code. **[local]** (installed addons) **[web]** (wiki)
- `GetBuildInfo()` returns `"1.60.1", <build>, <date>, 16001`. **[in-game]** (2026-09-23) **[dump]** (`client.interface = 16001`)
- `WOW_PROJECT_ID` is `WOW_PROJECT_CAMELOT` (18), not Retail's `WOW_PROJECT_MAINLINE` (1). `Blizzard_ProjectConstants` loads `Camelot\ProjectConstants.lua [AllowLoadGameType camelot]`, which sets `WOW_PROJECT_CAMELOT = 18; WOW_PROJECT_ID = WOW_PROJECT_CAMELOT`, since build 70170 (2026-10-01). **[web]** (the `forever` UI source, 70888) Self Test read `WOW_PROJECT_ID 18`. **[in-game]** (saved Self Test log, 2026-10-20) Before 70170 it was 1, same as Retail. **[in-game]** (2026-09-23) **[dump]** Still detect Forever by probing the API, or by the interface number below: an earlier build had it at 1.
  - So a Battle.net friend's `gameAccountInfo.wowProjectID == WOW_PROJECT_ID` means they're on Forever, not Retail: Blizzard's own `FriendsListUtil.IsPlayingSameWoWProject` (`Blizzard_FriendsFrame/Mainline/FriendsListUtil.lua`, loaded on every game type) is that test, and Camelot `FriendsFrame.lua` fades a friend's game icon when it fails. **[web]** (the `forever` UI source, 70888) What a Retail friend's field holds hasn't been seen in game: with one online, `/dump C_BattleNet.GetFriendAccountInfo(1).gameAccountInfo.wowProjectID` (the friend's index in the list) should say 1, and a Forever friend's 18.
- Launch is set for 2026-11-04. **[web]**

### Detecting Forever at runtime

Use the interface number with both ends of a range: `local iface = select(4, GetBuildInfo()); local isForever = iface >= 16000 and iface < 17000`.

- Never test "starts with 1" or "five digits": Classic Era is 11509 and would match. Manners' `Flavour.lua` explains this trap in detail. **[addon]**
- Many Retail addons test `>= 100000` to mean "modern client". On Forever that fails, so ported Retail code takes Classic paths. **[web]** (forever-addon-kit)
- Other addons use `[16000, 17000)` (WhisperMessenger, Manners) or `[16000, 20000)` (Auctionator, D4Lib, ManiaTip, AceDB in UnifiedProfileManager). **[addon]**
- Prefer probing the API you need over any version check.

## TOC and loading

- Ship one plain `ForeverPlusPlus.toc` with `## Interface: 16001`. That works. **[local]** (this addon loads and saves)
- **TOC suffixes: `_Camelot` wins on build 70009.** A test addon with `FppTocProbe.toc`, `FppTocProbe_Camelot.toc`, and `FppTocProbe_Mainline.toc`, all at 16001, loaded **`_Camelot`**. **[in-game]** (2026-09-25)
  - That matches warcraft.wiki.gg: expansion suffixes (`_Camelot`, `_Standard`, ...) beat family suffixes (`_Mainline`, `_Classic`), which beat the plain name. **[web]**
  - An earlier test on 2026-09-23 (`_Mainline` at 120100, `_Camelot` and plain at 16001) loaded **`_Mainline`**. **[in-game]** Either the build changed or the setup differed. Recheck after patches.
  - Installed addons that ship a `_Camelot.toc`: AutoStow, AzerothCompendium, Chatify, Manners, MapUtils, TwitchEmotes, WhisperMessenger. **[local]**
- **Per-file load conditions** in the TOC file list: `file.lua [AllowLoadGameType camelot]` and `[ExcludeLoadGameType ...]`.
  - The wiki lists game type `camelot` = Forever, `standard` = Midnight only, `mainline` = Midnight **and** Forever (plus Plunderstorm and other modes), `classic` = the Classic expansions. **[web]**
  - BugSack (`forever.lua [ExcludeLoadGameType standard, classic][AllowLoadGameType camelot]`), Auctionator (`Source_Forever\Constants.lua`), and AlreadyKnown (`[AllowLoadGameType classic, camelot]`) rely on this. **[addon]**
  - Auctionator also loads `[AllowLoadGameType mainline]` files on Forever and branches on `IsForever` inside them, which fits `mainline` including Forever. **[addon]**
  - Tested on Forever: `[AllowLoadGameType camelot]` and `[AllowLoadGameType mainline]` load, `[AllowLoadGameType standard]` and `[AllowLoadGameType classic]` don't, and `[ExcludeLoadGameType standard]` loads. **[in-game]** (2026-09-25, FppTocProbe)
  - So `camelot` (or excluding `standard`) splits Forever-only files from Retail at load time. `mainline` can't, since it matches both. That Retail skips `camelot` files comes from the wiki **[web]**; we didn't run the probe on Retail.
- `## Category`, `## IconTexture`, localized `## Title-xxXX` / `## Notes-xxXX` fields are used by installed Forever addons. **[addon]**

## SavedVariables

- **They persist now.** A load counter that only goes up when the saved table is read back reached 7 across sessions, and `WTF\Account\<acct>\SavedVariables\ForeverPlusPlus.lua` holds this addon's module state. **[local]** (checked 2026-09-25)
- History: on 2026-09-23 they were written but never read back, so every session started from defaults. **[in-game]** (the same counter stayed at 1) **[web]** (forever-addon-kit, EU forum thread)
- The fix landed by 2026-09-24. If settings stop sticking after a patch, check this first.
- Beta-era workarounds seen elsewhere, in case it regresses: `CreateMacro` survives a cold start; CVars registered with `C_CVar.RegisterCVar` survive `/reload` but not a restart. **[web]** (forever-addon-kit)

## Realms, names, and game rules

- Forever is realmless in the usual sense. Characters live under ruleset "realms" named like `Classic Beta PvE` and `Classic Beta PvP` in `WTF\Account\<acct>\`. **[local]**
  - Each ruleset realm spans several realm IDs in player GUIDs (`Player-<realmID>-<hex>`): OlympusMute's saved GUID-to-name table pairs 4618 and 4620 with `-classicbetapve`, and 4613 and 4619 with `-classicbetapvp`. **[local]** (its SavedVariables, 2026-10-23) So key players by realm name, never by the GUID's realm ID. `Lib/Players.lua` takes it from `GetPlayerInfoByGUID`'s seventh value (empty for the player's own realm, on Retail) or `GetRealmName()`.
- `UnitName` returns a **surname** as its second value, not a realm: `UnitName("player")` gave `"Clutch", "Bloodfury"`. **[in-game]** (2026-09-25) `C_PlayerInfo.ShouldDisplaySurname()` exists. **[dump]** **[addon]** (Chatify's mention code)
  - Names can appear as `First Surname` or `First-Surname`; never parse the part after `-` as a realm. **[addon]** (Chatify `Config.lua`)
  - ManiaTip hides realm text on Forever. **[addon]**
- AceDB (in UnifiedProfileManager and Manners) keys profiles by ruleset on Forever, using `C_GameRules.IsGameRuleActive(Enum.GameRule.HardcoreRuleset / RPRuleset / PvPRuleset)`. **[addon]**
- Beta game rules reported active: `DisableCampsites`, `TransmogEnabled = 0`, `EncounterJournalDisabled`. **[web]** (forever-addon-kit)
- `MicroMenu:GenerateButtonInfos()` lists the micro buttons, and some carry a `gameRule` that hides them. D4Lib uses that on Forever instead of a hard-coded list. **[addon]**

## Namespaces that exist

From the dumps **[dump]**: `C_AddOns`, `C_Item`, `C_Spell`, `C_Container`, `C_UnitAuras`, `C_TooltipInfo`, `C_QuestLog`, `C_Map`, `C_ChatInfo`, `C_EditMode`, `C_Traits`, `C_ClassTalents`, `C_SpecializationInfo`, `C_GameRules`, `C_PlayerInfo`, `C_Secrets`, `C_RestrictedActions`, `C_CurveUtil`, `C_EncodingUtil`, `C_DamageMeter`, `C_SwingTimer`, `C_CooldownViewer`, `C_AuctionHouse`, `C_TradeSkillUI`, `C_SeasonInfo`, `C_AddOnProfiler`.

- Retail-only systems also exist in the API (`C_MythicPlus`, `C_ChallengeMode`, `C_Garrison`, `C_DelvesUI`, `C_Housing`, `C_Transmog`, `C_CraftingOrders`, `C_EncounterJournal`, `C_LFGList`). Existing is not the same as usable: the content may be off. Don't build on them without checking in game.
- There is no `C_Seasons`, `C_Engraving` (Season of Discovery), `C_ClassicPlus`, or `C_Camelot`. **[dump]**
- The UI helpers `Settings`, `Menu`, `MenuUtil`, `TooltipDataProcessor`, `ChatFrameUtil`, and `BackdropTemplateMixin` are tables, so the dumps (functions and named frames) don't list them. `Settings.RegisterAddOnCategory`, `Menu.ModifyMenu`, and `TooltipDataProcessor.AddTooltipPostCall` are all functions. **[in-game]** (2026-09-25, `/dump`) The others are used by installed Forever addons **[addon]**; probe before use.
- Tooltip line pre calls: `TooltipDataProcessor.AddLinePreCall(lineType, fn)` runs `fn(tooltip, lineData)` before each line of that `Enum.TooltipDataLineType` is added, and a true return leaves the line out and stops the pre calls after it (`TooltipDataHandlerMixin:ProcessLineData`). A line added gets `lineData.lineIndex`, its number in the tooltip; a line left out has none, so the lines after it no longer sit at their place in `data.lines`. `QuestObjective` (8), `QuestTitle` (17), and `QuestPlayer` (18) are line types, and `Unit` (2) and `Object` (4) tooltip types; the tooltip being built is `tooltip:GetProcessingTooltipInfo().tooltipData`. **[web]** (the `forever` UI source, `Blizzard_SharedXMLGame/Tooltip/TooltipDataHandler.lua` and `Blizzard_APIDocumentationGenerated/TooltipInfoSharedDocumentation.lua`, build 70862, checked 2026-11-07) Not yet seen in game.
- Settings pages: `Settings.RegisterVerticalLayoutCategory`, `Settings.RegisterProxySetting(category, variable, Settings.VarType.Boolean, name, default, get, set)` with `Settings.CreateCheckbox`, and `CreateSettingsListSectionHeaderInitializer` are used this way by BugSack `config.lua` and ArcaneWizardLibrary. **[addon]** `Settings.NotifyUpdate` (to refresh a checkbox changed from `/fpp`) is **Unverified**; Forever++ probes for it.
- Named frames present **[dump]**: `AddonCompartmentFrame`, `EditModeManagerFrame`, `MicroMenu`, `ObjectiveTrackerFrame`, `ContainerFrameCombinedBags`, `CooldownViewerSettings`, `DamageMeter`, `PlayerFrame`, `TargetFrame`, `BuffFrame`, `MinimapCluster`, `CharacterFrame`, `WorldMapFrame`, `MerchantFrame`, `GossipFrame`, `QuestFrame`, `LootFrame`.
- The addon compartment: Manners registers with `AddonCompartmentFrame:RegisterAddon({ text, icon, notCheckable, registerForAnyClick, func, funcOnEnter, funcOnLeave })`, reading the mouse button from `func`'s second argument as `input.buttonName`, and Lootified uses the TOC's `AddonCompartmentFunc` fields. There's no unregister: LibDBIcon (bundled with Manners) removes its entry from `AddonCompartmentFrame.registeredAddons` and calls `UpdateDisplay()`, and Minimap Button does the same to toggle live. **[addon]** (2026-10-03) That the removal and the click data work on Forever is **Unverified** in game.
- Not in the named-frame dump, likely load-on-demand or missing: `ProfessionsFrame`, `AuctionHouseFrame`, `PlayerSpellsFrame`, `ClassTalentFrame`, `SpellBookFrame`. **Unverified.** Hook them on `ADDON_LOADED`, and check they exist.

## Talents and specs

- Classic-style talent trees with points per tree, on Retail's trait system (`C_Traits`). A separate "Legacy" tree panel opens with `ToggleLegacySystemUI` and unlocks at level 25. **[web]** (forever-addon-kit)
  - Its trees are trait trees: `Constants.LegacyConsts` names Professions 1187, Adventure 1188, and Progression 1189, the Legacy points currency 4225, and `LEGACY_TREE_ADVENTURE_TALENTED_NODE_ID` 110298. Blizzard's Legacy panel reads a tree with `C_Traits.GetConfigIDByTreeID(treeID)`. **[web]** (Gethe/wow-ui-source `forever` branch, Blizzard_LegacySystem and LegacyConstantsDocumentation, 2026-10-11) Unverified in game.
  - Talented (that node, 5 ranks) gives talent points from level 5 instead of 10, still 51 at most, by its 5/5 tooltip. **[in-game]** (2026-10-11) What fewer ranks do is **Unverified**; Talent Planner takes a level earlier per rank, and counts from the points earned whenever it can.
- `C_SpecializationInfo.GetSpecializationInfo(index, ...)` returns `specId, name, description, icon, role, primaryStat, pointsSpent, background, previewPointsSpent, isUnlocked`. **[dump]** (Atraeau api.json)
  - On a Warrior, `GetSpecializationInfo(1)` returned `1491, "Warrior", "", 626008, "DAMAGER", 4, 0, nil, 0, true`, and `C_SpecializationInfo.GetSpecialization()` returned `1`. **[in-game]** (2026-09-25)
  - So the "spec" is the whole class: the name is the class name, the description is empty, and `pointsSpent` was 0 with 6 points spent in Arms. It doesn't count talent points, so it can't find a talent tree.
  - D4Lib picks the tree with the most `pointsSpent` as the player's "spec" **[addon]**. Given the result above, that finds nothing, and it passes a table where the dump documents positional arguments.
- Spec IDs are new (Warrior 1491 **[in-game]**; Paladin 1486 **[web]**), so Retail spec-ID tables are wrong here.
- Talent points live in `C_Traits`, in a config of a Forever-only type. **[in-game]** (2026-09-25, Warrior with 6 points in Arms)
  - `Enum.TraitConfigType` has `Invalid 0, Combat 1, Profession 2, Generic 3, CamelotCombat 4`.
  - `C_ClassTalents.GetActiveConfigID()` returned a `CamelotCombat` config named `"Warrior"` with a single tree, `treeIDs = { 1117 }`. There is no Retail-style `Combat` config.
  - `C_Traits.GetTreeCurrencyInfo(configID, 1117, false)` returned one currency (3820) with `spent = 6, quantity = 0, maxQuantity = 6`. That's the total across all three talent tabs, not per tab.
  - The tabs are trait **groups**. `C_Traits.GetGroupDisplayInfoByTreeID(1117)` returned three entries with `groupID`, `displayName`, `icon`, `orderIndex`, and `skillLineID`: Arms 11650, Fury 11657, Protection 11670.
  - Purchased nodes (`C_Traits.GetNodeInfo(configID, nodeID)`) have `subTreeID = nil`, and `posX` / `posY` in tree coordinates. Two Arms nodes had `groupIDs[1] = 11650`; a third had `groupIDs[1] = 11649`, a group that isn't a tab.
  - A node's tab is whichever of its `groupIDs` matches a display group, not the first one. That third node's `groupIDs` were `{ 11649, 12820, 12821, 12822, 12823, 12824, 11650 }`: the tab (11650) came last. What 11649 and 12820-12824 gate (tiers?) is unknown.
  - **Points per tab:** `C_Traits.GetGroupCurrencyInfo(configID, { 11650, 11657, 11670 })` returned `{ traitNodeGroupID = 11650, currencyInfos = { { traitCurrencyID = 3820, spent = 6, quantity = 0, maxQuantity = 6 } } }`. Fury and Protection, with nothing spent, were left out of the result entirely, so treat a missing group as 0.
- The talent window is `PlayerSpellsFrame.TalentsFrame` from load-on-demand `Blizzard_PlayerSpells`, with Camelot files (`[Game]/ClassTalents/...`, `[AllowLoadGameType camelot]`) over Mainline's shared talent frame (`Blizzard_SharedTalentUI`). **[web]** (Gethe `forever` branch, 2026-10-03)
  - Talents are staged and learned with the Apply Changes button (`ApplyButton`), as on Retail. Nodes use the square art set (`talents-node-square-*`); talent buttons hide with alpha 0 for the Invisible state (`TalentDisplayMixin:SetVisualState`).
  - The loadout dropdown (`LoadSystem`) is hidden, the search box stays, and there are no PvP talents. A primary and secondary tab are spec groups, the second locked until dual spec (`GetNumSpecGroups() > 1`).
  - Tab headers (`frame.treeHeaders`, each with `displayInfo` and a `Text` of points spent) are rebuilt by `RefreshTreeHeaders`, from `GetGroupCurrencyInfo`. Row gates come from `C_Traits.GetTreeInfo(...).gates` and the nodes' gate conditions (`isGate`, `spentAmountRequired`).
  - `EventRegistry` fires `TalentFrameBase.ButtonsUpdated` after the buttons update and `TalentDisplay.TooltipCreated` (button, tooltip) after a talent tooltip is shown.
- Popups with a text box (`hasEditBox`) reach it through `dialog:GetEditBox()`, and call a dialog's `EditBoxOnEnterPressed(editBox, data)` and `EditBoxOnEscapePressed`. Menu dropdowns are Mainline's `DropdownButton` with `WowStyle1DropdownTemplate` and `SetupMenu`. **[web]** (Gethe `forever` branch, `Blizzard_StaticPopup`, `Blizzard_Menu`, 2026-10-04)
- A popup shows up to four buttons (`button1`..`button4`), left to right in index order, sized to fit. `StaticPopup_OnClick` calls `OnAccept` for button 1, `OnAlt` for 3, and `OnCancel` for 2 and 4, unless the dialog sets `selectCallbackByIndex`: then it calls `OnAccept` (or `OnButton1`), `OnCancel` (or `OnButton2`), `OnButton3`, and `OnButton4`, and hides the popup unless the function returns true. Escape calls `OnEscape`, or `OnCancel`. `ns.ConfirmChoice` uses that for a third choice. **[web]** (Gethe `forever` branch, `Blizzard_StaticPopup/StaticPopup.lua` and `Blizzard_StaticPopup_Game/GameDialog.lua`, 2026-11-10) Unverified in game.
- `MenuUtil.CreateContextMenu` opens at the cursor (the menu's TOPLEFT on it) and never flips sideways: at the screen's edge it flips up and is clamped back on. A menu beside a frame goes through `Menu.PopulateDescription` and `Menu.GetManager():OpenMenu(owner, description, AnchorUtil.CreateAnchor(...))`, which flips on either axis. **[web]** (Gethe `forever` branch, `Blizzard_Menu/Menu.lua` and `MenuUtil.lua`, 2026-10-16) Unverified in game.
  - Talent Planner reads a row's points from a node's gate condition when it has one, counted in the node's tab as Classic does, and otherwise as 5 per row from `posY`.
  - `GameTooltip:AppendInfo("GetTraitEntry", entryID, rank)` adds Blizzard's text for a rank to a tooltip of our own. The first time a talent is shown its spell isn't loaded, and when it loads `GameTooltip:RefreshData()` redraws the tooltip from the appended data alone, dropping every line we added. Hooking `RefreshData` and drawing ours again while our button owns the tooltip fixed it. **[in-game]** (2026-11-08, Talent Planner)
  - Nodes of one row don't always share a `posY`: on a warlock's Affliction tab, two of the top row's three talents sat a little lower than the third, so taking the smallest gap between heights as a row made them need 5 points and the second row 305. **[in-game]** (2026-11-08, Cameron's screenshots) `TalentPlan.RowGates` now treats a gap under a quarter of the largest as a node nudged within its row. Whether Forever's gate conditions count tab or tree points is **Unverified**. Talent points from level 10 are inferred from Classic; the planner calibrates from points earned (spent plus unspent) once there are any.

## Secret values and combat data

Forever inherits Midnight's addon restrictions. `AGENTS.md` has the rules for writing code; this is the evidence.

- `issecretvalue`, `canaccessvalue`, `issecrettable`, `scrub`, `secretwrap` exist, as does `C_Secrets` with 27 predicates (`HasSecretRestrictions`, `ShouldAurasBeSecret`, `ShouldUnitHealthMaxBeSecret`, `GetSpellAuraSecrecy`, ...). **[in-game]** (2026-09-23) **[dump]**
- In a solo open-world fight, `UnitHealth`, `UnitHealthPercent`, and `UnitHealthMissing` were secret for player and target, and the target's `UnitHealthMax` was secret. The player's `UnitHealthMax` and all `UNIT_COMBAT` amounts stayed readable. **[web]** (forever-addon-kit)
- The player's own mana is secret even out of combat: `UnitPower("player", 0)` printed "(hidden by the game)" and `issecretvalue` was true, on a level 1 druid in the open world. Its max read fine, since Druid Mana Bar's bar showed, and that needs a readable max. **[in-game]** (2026-11-05, `/dump`) So bar text of ours goes through `SetFormattedText`, which takes a secret. Whether `AbbreviateLargeNumbers` and `UnitPowerPercent(unit, powerType, false, CurveConstants.ScaleTo100)` take one too here is **Unverified**; Druid Mana Bar tries them under `pcall`.
- In combat, while `C_Secrets.ShouldAurasBeSecret()` is true, reading a secret aura throws, including your own buffs. Secrecy is per spell: `C_Secrets.GetSpellAuraSecrecy(id)`. **[web]** On Forever, `C_UnitAuras.GetAuraDataByIndex("player", i, "HELPFUL")` from addon code threw "Auras cannot be accessed when secret while tainted" on the player's own buffs, after casts in combat. **[in-game]** (2026-10-14, Error Catcher, 149 times in a session) `ns.AurasReadable()` checks `ShouldAurasBeSecret` before a read.
- Forever's buff frame works out each aura's time left in its own Lua (`AuraButtonMixin:CalculateTimeLeft`, `expirationTime - GetTime()`) every frame and passes it to `AuraButtonMixin:UpdateDuration(timeLeft)`, so that number reaches a `hooksecurefunc` on a button's `UpdateDuration`. **[web]** (Gethe `forever` branch, `Blizzard_BuffFrame/BuffFrame.lua:1193-1235, 1387-1400`, checked 2026-10-10) Whether it comes back secret for your own auras in combat on Forever is **Unverified**; Buff Timers checks `ns.IsReadable` each frame and leaves Blizzard's text showing when it isn't.
- Blizzard's player buff frame has no sort option: no Edit Mode setting (the Aura frame's are Orientation, Icon Wrap, Icon Direction, Icon Size, Icon Padding, Icon Limit, Opacity, Visibility, Show Dispel Type) and no CVar read for one (`buffDurations`, `consolidateBuffs`, `collapseExpandBuffs`, `displayTemporaryEnchantIcon`, `GamepadShowAutoAuraTooltip`). Buffs show in the order `AuraUtil.ForEachAura` returns them, after weapon enchants: `AuraFrameMixin:UpdateAuraButtons` gives `auraFrames[i]` the i-th entry of `self.auraInfo`, and `AuraContainerMixin:UpdateGridLayout` lays all of `BuffFrame.auraFrames` out in index order (only Edit Mode changes, consolidation, and load run it, not each aura update). The buttons are plain `AuraButtonTemplate` Buttons (no secure template); a right-click runs Blizzard's own `AuraButtonMixin:OnClick`, which calls `CancelUnitBuff(PlayerFrame.unit, self.buttonInfo.index, ...)`. Whether untracking drops the super-tracked quest (it restores it if so) is **Unverified**.
- Whether an inline atlas taller than the font makes its line taller (which would shift the rows under a marked title by a few pixels in the quest log and tracker) is **Unverified**. Forever Quest Icons only checks that the icon adds no line.

## Calendar and realm time

- The clock's Use Local Time box is the CVar `timeMgrUseLocalTime`, and only `GameTime_GetTime()` reads it (the minimap clock and its tooltip). The calendar formats every time from `C_Calendar`'s realm hour and minute with `GameTime_GetFormattedTime(hour, minute, wantAMPM)`, which only formats, so the box never reaches it. The places: the month grid (`CalendarFrame_UpdateDayEvents`, AM and PM only while a day shows 2 events or fewer), a day's tooltip (`CalendarDayButton_OnEnter`), the picker for a day with more than 4 (`CalendarEventPickerFrame_InitButton`), the view event, holiday, and raid windows, an invitee's answer time (`CalendarEventInviteListButton_OnEnter`), and the create event window's hour and minute dropdowns, which send realm time with `C_Calendar.EventSetTime`. Outside the calendar: the Communities window's calendar button tooltip and its event lines in chat (`CalendarUtil`), Guild News events (`CommunitiesGuildNewsButton_SetEvent`), and a sale invoice's money arrival time (`OpenMailMixin:Update`, from `GetInboxInvoiceInfo`'s `etaHour`, `etaMin`). Everything else that reads `GetServerTime()` counts down. **[web]** (Gethe/wow-ui-source `forever` branch at 1.60.1.70862, `Blizzard_Calendar/Mainline/Blizzard_Calendar.lua`, `Blizzard_FrameXMLUtil/GameTimeUtil.lua` and `CalendarUtil.lua`, `Blizzard_Communities`, `Blizzard_MailFrame/MailFrame.lua`, checked 2026-11-07)
- The view windows keep their update function from load (`self.update = CalendarViewEventFrame_Update`), and `CalendarFrame_ShowEventFrame` calls that copy when a window is already shown, so a hook on the global misses those redraws; Local Time hooks `CalendarFrame_ShowEventFrame` and each window's OnShow too. The day buttons' OnEnter is an inline script that calls `CalendarDayButton_OnEnter` by name, and invite buttons take `CalendarEventInviteListButton_OnEnter` each time they're set up, so hooks on those globals are reached. **[web]** (same source)
- `C_DateAndTime.GetCurrentCalendarTime()` is the realm's date and time to the minute; Local Time's offset is that against `date("*t")`, rounded to a quarter hour. That the mail's `etaHour` is realm time, like the calendar's, is **Unverified**; check a sale invoice against the realm clock (the money comes an hour after the sale).
- `C_Calendar.GetDayEvent`, `EventGetInvite`, `EventGetInviteResponseTime`, and `GetClubCalendarEvents` are `SecretInChatMessagingLockdown`: their answers are secret "when encounter, challenge mode, or PvP match addon restrictions are in effect, and when the player is on a communication-restricted map such as a dungeon or raid". No other calendar or date call is marked, so `C_DateAndTime.GetCurrentCalendarTime` and the `CalendarTime` structure (`TimeDocumentation.lua`) are never secret. **[web]** (the `forever` UI source, 70888, `Blizzard_APIDocumentationGenerated/CalendarDocumentation.lua` and `SecretPredicatesDocumentation.lua`) Whether such an answer is a secret table or a table of secret fields isn't said; Local Time checks both.

## Files an addon can reach while the game runs

Learned while building a link between the addon and a program outside the game (Agent Chat, since removed). "The program" below is that outside program.

- `C_AddOns.SaveAddOns()` writes the character's `WTF\Account\<account>\<realm>\<character>\AddOns.txt` at once, no `/reload`: a line `Name: enabled` or `Name: disabled` per addon. **[in-game]** (2026-11-07, build 70862) `C_AddOns.EnableAddOn(name, UnitGUID("player"))` changes only the current character's file (as Blizzard's AddOns list does); a name alone (`UnitName("player")`) changes nothing; no character at all changed three of six characters' files on the account. 256 helper addons, each one bit, flipped and saved in about a millisecond. Forever's character folders are named `<Name>-<Surname>`.
- `C_AddOns.LoadAddOn` reads a load-on-demand addon's files from disk when it loads, so a file rewritten after the game started is read as rewritten. A reply written by the program came back in 51 ms. **[in-game]** (2026-11-07) The addon itself must exist when the game starts; new addon folders need a full restart (every Forever AI bridge project says so **[web]**).
- The game knows only the loose files in an addon's folder that existed when it started. **[in-game]** (2026-11-07) For those, `PlaySoundFile(path, "Master")` checks the disk each time it's called: false while the file is deleted, true again within 49 ms of it being made, across `/reload` too. That holds with Enable Sound off and after tabbing out. A name made after the game started is never found. An empty (0-byte) file counts as there. Once a sound has been found, it reads as there until the game restarts, even after it's deleted (a slot used before a `/reload` still read as there after it).
- `FontString:SetFont(path)` never succeeded with a real font (Marlett) the program made or filled in after the game started, under a known name or a new one. `GetFileIDFromPath` never found a file made after the start either. `Texture:SetTexture(path)` returned true for a file that didn't exist. None of them can tell. **[in-game]** (2026-11-07)
- `C_Log.LogMessage` text didn't reach any file in `Logs` within a minute. **[in-game]** (2026-11-07)
- The `## Group` TOC field puts an addon under another one in the AddOns list: it must exactly match the parent addon's folder name. **[web]** (the `forever` UI source, `Blizzard_AddOnList/AddonList.lua` `AddonList_Update`, build 70862) Unverified in game.
